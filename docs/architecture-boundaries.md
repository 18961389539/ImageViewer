# Architecture Boundaries

The WPF control remains the delivery surface. Modernization separates new code by dependency direction instead of moving existing WPF-bound types in one disruptive change.

## Dependency Rule

`ImageViewerControl` may depend on WPF, the rendering backend, and `ImageViewer.Core`. `ImageViewer.Core` targets `net8.0` and `net10.0` and must not reference `System.Windows`, `System.Windows.Media`, `Dispatcher`, or WPF bitmap types.

## Code Placement

- Put UI controls, bindings, dialogs, dispatcher scheduling, bitmap decoding, and render frames in the WPF project.
- Put new immutable data contracts, geometry algorithms using primitive coordinates, serialization formats, import/export schemas, and cancellation-aware analysis orchestration in `ImageViewer.Core`.
- Keep adapters at the WPF edge: convert `Point`, `Color`, and `BitmapSource` into core contracts before calling core services.

The first migrated slices are measurement statistics, geometry values, and persistence schemas. `ImageViewer.Core.Measurements.MeasurementStatistics` owns filtering, sorting, and aggregate calculations for dual-edge width samples. `ImageViewer.Core.Geometry.Geometry2D` owns framework-neutral distance, polygon, angle, centroid, and bounding-box operations. `PointD`, `RectD`, and `VectorD` are defined by Core; the WPF assembly keeps type-forwarders so existing consumers continue to resolve the old model type names. `ImageViewerControl.Models.CaliperWidthMeasurementResult` remains the compatibility-facing adapter and delegates those rules to Core. Session envelopes, ROI documents, camera calibration, and their source-generated JSON metadata now live in `ImageViewer.Core.Persistence`/`ImageViewer.Core` while the WPF session service retains file and plugin orchestration.

Volume orientation and slice provenance (`VolumeSliceOrientation`, `VolumeSliceProvenance`, and `VolumeSliceOrderMetadata`) are also framework-neutral Core contracts. `VolumeData`, bitmap reconstruction, 3D scene models, and MPR scheduling remain WPF adapters around those contracts.

Analysis execution is represented by `ImageViewer.Core.Analysis.IAnalysisStage<TContext>` and `IAnalysisPipeline<TContext>`. The WPF adapter composes histogram and profile stages through that contract; bitmap access and render services stay at the edge.

Analysis results are committed only while their request is still current. Each histogram, profile, and pyramid request receives an `ImageViewerAnalysisTicket` from `ImageViewerAnalysisState`; the ticket carries a monotonic sequence and its own cancellation source, the state keeps only the newest ticket per kind, and a request that is no longer current drops its result instead of presenting it. `ImageViewerAnalysisState.Snapshot` is an immutable `ImageViewerAnalysisSnapshot` holding the analysis bitmap, pyramid levels, and a `SourceGeneration` that is bumped by `ResetForSource` (the only writer). `SetPyramidLevels` rejects results whose generation no longer matches, so switching images cannot be overwritten by work started for the previous one. Request tickets and the source generation cover different races and both are required: tickets stop an older request from overwriting a newer one on the same image, while the generation stops any pre-switch work from landing after `ResetForSource`. This mirrors the generation pattern already used by `ImageViewer.DialogWorkflowService` (image loads), `AdaptiveImageViewer` (MPR slices), and `ImageViewerRenderTileCache` (prefetch).

Persistence follows the same "capture on the UI thread, then hand off" rule. `CaptureSnapshot` (session persistence and auto save) converts ROIs into a detached `RoiDocument` on the UI thread, so `ImageViewerPersistenceSnapshot` carries plain data instead of a reference to the live `ViewerState.AllRois` collection. Serialization and packaging may therefore run on a background thread: `ImageViewerSessionService.SaveToFileAsync` and `RoiPersistenceService.SaveToFileAsync` offload JSON writing, and `ImageViewerProjectPackageService.ExportAsync` performs the whole ZIP build (including image compression) inside `Task.Run` with an async entry copy so large exports stay cancellable. The ordering is not optional: offloading first would serialize a collection the editor is still mutating.

Caliper detection result contracts (`CircularCaliperDetectionResult`, `LineCaliperDetectionResult`, and `LineMeasureGradientDetectionResult`) now use `PointD` and Core line-fit geometry. Legacy WPF result records remain conversion shims for existing callers; production mapping and rendering consume the Core contracts.

The 2D/3D/MPR boundary is owned by `AdaptiveImageViewer`: it selects the active surface, coordinates slice and plane selection, and cancels stale MPR requests. `VolumeSliceService` keeps normalized intensity planes and a bounded per-volume LRU slice cache, while `ImageViewerRenderTileCache` provides a bounded LRU tile cache for large 2D frames. Both caches are invalidated when their source or render generation changes, so background work cannot publish stale pixels.

Rebuilding an MPR plane is single-flight: `VolumeSliceService` keys a `Lazy<Task<BitmapSource>>` by (orientation, index), so dragging over one index reconstructs it once and every caller shares that result — which also doubles as the slice cache (a 64 MB bounded LRU over completed plans). The shared build is deliberately **detached from caller tokens**: a caller waits with its own token (`WaitAsync`) and may abandon, but a single abandoned drag must not cancel work other callers are waiting for. The consequence is that a build started for a plane the user has already left still runs to completion and stays cached, which makes dragging back to it instant. An entry's lifecycle is decoupled from its callers: a continuation attached exactly once (CAS) registers the completed slice with the budget and removes the entry on failure, so results are always accounted even when every caller has cancelled, and a faulted build is never cached. Waiting callers only touch the LRU for recency. An index outside the volume's range throws before any entry is created. MPR pixel extraction itself needs no normalization cache: `ImageViewerPixelAccess.NormalizeForIntensity` returns the same instance for the common formats and only wraps exotic ones in a lazy `FormatConvertedBitmap`, so building a plane costs one row/column read per axial slice — proportional to the output plane, not to the volume.

Pseudo-color and display adjustment have exactly one definition, in C#. `ImageViewerDisplaySourceService.GetDisplayLut` composes a 256-entry BGRA table from the transfer curve (`ImageViewer.Core.Display.DisplayTransfer`, which owns window/level, brightness, contrast, gamma and invert) and the palette ramps, and the shader samples that very table as a second sampler input (`DisplayLut`, register `s1`), so the CPU fallback and the GPU path cannot drift apart: intensity uses the same weights (`ImageViewerPixelAccess.ReadIntensity`, i.e. 0.299/0.587/0.114) and the same value mapping (16-bit as `v/257`, which is the shader's `intensity * 255`), alpha follows one policy (input alpha is preserved for `Bgra32`/`Pbgra32`, everything else is opaque), and the LUT is sampled at texel centers so the CPU's integer index and the GPU's lookup land on the same entry. One flag decides the indexing mode for both paths (`ImageViewerDisplaySettings.UsesPerChannelIndex`): with a palette the table is indexed by intensity, without one it is indexed per channel so adjusting an RGB image keeps its colors (gray formats are numerically identical either way). The palette definitions live only in `GetPaletteColor` and the transfer curve only in Core; the shader carries neither, and a test asserts that by reading the shader source. Shader source is embedded as a WPF `<Resource>` and read back from the `<assembly>.g.resources` container (WPF ignores non-XAML `EmbeddedResource` items, which is how the GPU path could be silently dead while `PreferShaderPseudoColor` looked implemented). A display change only refreshes the rendered image: histogram/profile computation reads the raw intensity bitmap and their rendering uses fixed colors, so neither depends on display settings. The non-tiled path shares the same cache — the whole image is simply one tile entry — so a colorized frame is computed once, reused by instance across repeated frames, and always accounted against the budget (it used to re-colorize the full image on every refresh, ~15 MB of BGRA copies for a 4 MP image, outside any budget).

The tile cache stores one entry per (source, grid-aligned rect, `ImageViewerDisplaySettings`) — the colorized tile, which is what the budget accounts for — and derives the visible crop as a view hanging off that entry, so repeated frames get the same instance (no per-frame texture re-upload) while no entry can pin pixels it does not account for. The whole display settings value is part of the key, so a palette or adjustment change can never reuse stale pixels; old entries age out through the LRU. Prefetching is speculative and therefore bounded and cancellable: a pending-queue cap and a concurrency cap keep a fast pan from flooding the thread pool, `Clear()` cancels queued work instead of letting it burn CPU while discarding the result, and prefetch skips non-frozen sources because a pool thread may not touch a thread-affine `BitmapSource` (the analysis bitmap is always frozen by `ImageViewerDisplaySourceService.GetAnalysisBitmap`). Prefetch writes the same key and applies the same display transform as the visible path, otherwise a prefetched entry would either be unusable or get displayed as if it were already processed.

Command controllers depend on capability interfaces. View options, viewport operations, image transforms, analysis options, analysis operations, drawing modes, ROI selection/editing, file operations, and feature analysis/export/feedback are composed by small adapters. The command composition root no longer constructs large delegate bags; each controller receives only the capabilities it uses.

ROI plugins expose capability interfaces (`IRoiPluginDefinition`, `IRoiCollectionCapability`, `IRoiPersistenceCapability`, `IRoiInfoCapability`, and `IRoiEditorCapability`). `IRoiPlugin` remains the compatibility aggregate used by the registry while consumers can depend on the smallest capability they need.

Plugin *discovery* is scoped by two explicit declarations and never by "whatever happens to sit next to the executable". An unconfigured `PluginDirectoryPath` resolves to `<application directory>/plugins` and never falls back to the application directory itself. `AllowedAssemblyNamePrefixes` is required: an empty list loads and scans nothing and logs a warning, so the set of plugin assemblies is always declared rather than inferred. Directory entries are filtered by file name first (a non-candidate file is never opened, which also keeps non-managed DLLs from producing a warning each) and the assembly metadata name is checked again afterwards. `RegisterFromAssemblies` is the deliberate exception: it takes an explicit assembly list from the caller and is therefore not prefix-filtered.

Unloading has two distinct meanings here. *Logical* unload already works: `RoiPluginDiscoveryOptions.UnloadedPluginTypeKeys` (and `DisabledPluginTypeKeys`) are applied through `ApplyPluginFilters`, which unregisters the plugin, which now also migrates ROI state. *Assembly* unload is not possible today because discovery loads through `AssemblyLoadContext.Default`; the assembly and its types stay loaded for the process lifetime. Making it possible is a separate change and must respect these constraints: only the plugin's own assemblies may go into a collectible context while framework and shared dependencies must resolve through the default context (returning null from `Resolving`), and `Unload()` only collects once nothing references the context — in this codebase that includes `IRoiPlugin` instances, cached `Type` values, and the ROI objects the plugin created, so it only becomes reachable in combination with the migration that drops ROIs of unknown types. Per-module granularity is usually the right choice, and collectible contexts carry performance and diagnostics costs worth documenting before they are enabled.
Plugin registry changes are explicit migrations rather than implicit re-computation. `ImageViewerPluginRuntimeState` funnels both change paths — swapping in another `RoiPluginRegistry` instance and mutating the current one in place (`Register`/`Unregister`, surfaced through `RoiPluginRegistry.Changed`) — into `ImageViewerViewModel.ApplyPluginRegistryChange`, which drops the per-type cached collections (unsubscribing them so a stale reference cannot re-inject ROIs), re-adds the ROIs the new registry still knows, clears selection when the selected ROI's type is gone, and clears the undo stack (its commands silently no-op once `FindByRoi` returns null). ROIs whose type the registry no longer knows are removed from the live state but serialized into unresolved payloads (`RoiPersistenceData`) using the last plugin that was seen for their type — kept in `ImageViewerPluginRuntimeState` precisely because the owning plugin may already be gone when the migration runs — and appended to the session's `UnresolvedRois` channel, which saves write back verbatim (a merge, not the wholesale replace used when loading). This is why a dropped annotation survives the next save and returns once its plugin is installed again. Keeping them in the live collections instead would break the save: `RoiPersistenceService.CreateItem` throws for a type with no registered plugin. `RoiPluginRegistry.BeginUpdate()` coalesces a module's registrations into one `Changed` notification, which fires synchronously **on the caller's thread** — a subscriber must marshal to the UI thread before touching collections or visuals, and the control does exactly that through a migration scheduler injected at bootstrap (fast-path when already on the dispatcher, queued migrations discarded after detach). Each viewer detaches from the registry when disposed, since a registry instance can be shared.

## Package Layout And Core Namespaces

Persistence contracts live in `ImageViewer.Core.Persistence` (and volume contracts in `ImageViewer.Core.Volume`) — the framework-neutral assembly must not borrow the `ImageViewer.Services` / `ImageViewer.Plugins` / `ImageViewer.Controls` namespaces of the WPF layer, because a domain type named after a plugin mechanism inverts the dependency direction. `CoreArchitectureBoundaryTests.CoreNamespaces_AreLayeredInsteadOfBorrowingUiOrPluginNamespaces` enforces this, and `SharedContracts_AreOwnedByCoreAssembly` pins where each shared contract lives. Moving a type between namespaces changes its identity: this is a breaking change for already-compiled third-party plugin assemblies, and a `[TypeForwardedTo]` entry cannot fix it (forwarding requires the identical full type name).

Image analysis — caliper edge sampling, robust line/circle fitting, and blob segmentation — is framework-neutral managed code in `ImageViewer.Core.Analysis` (`CaliperAlgorithm`, `RobustFitAlgorithm`, `BlobAlgorithm`, and the `IntensityImage` plane, with the `CaliperEdge`/`CaliperEdgePair` and `BlobFeature` result records). `ImageViewerControl` keeps one WPF edge adapter, `VisionAlgorithmEntryPoint`, which decodes a `BitmapSource` into an `IntensityImage` and converts WPF `Point`/`Vector` values into `PointD`/`VectorD` (and the results back) at the boundary. `LineFitMode` and `CaliperEdgePolarity` are Core-owned too; they keep the `ImageViewer.Models` namespace and the control forwards them, so already-compiled plugins still resolve. There is no native runtime asset to package or load, so the control is no longer restricted to win-x64 processes; it runs on any architecture supported by its `net8.0-windows`/`net10.0-windows` WPF target.

## Host, Viewer, And Runtime Lifetime

The control, its host, and the runtime services it uses form one ownership chain with a single rule: **whoever creates the runtime services releases them**. `ImageViewerHost.OwnsRuntimeServices` states which side that is.

| Role | Created by | Released by | Reusable after release |
| --- | --- | --- | --- |
| `ImageViewerRuntimeServices` (+ its `ImageViewerRenderService` when it created one) | container registration, `ImageViewerHostBuilder.UseRuntimeServices`, or `ImageViewerHostDefaults.CreateRuntimeServices` | the creator: the DI scope, the caller, or an owning host | yes for container-owned instances (one per scope) |
| `ImageViewerHost` | container registration or `ImageViewerHostBuilder.Build()` | container scope, or the last viewer lease when the host owns the runtime | an owning host stops accepting `CreateViewer()` after the runtime is released |
| `ImageViewer` | `ImageViewerHost.CreateViewer()`, `new ImageViewer()`, or container scope | `Dispose`/`DisposeAsync`, which returns the host lease exactly once | no |

Rules that keep the chain closed:

- Every viewer, whether built by hand or resolved from a container, registers a lease in the viewer constructor and returns it from its lifetime scope (`ReleaseHostLease` is also a lifetime cleanup, so an earlier cleanup failure cannot strand the lease).
- An owning host releases its runtime with the **last** viewer lease, so a host that creates several viewers does not pull the runtime out from under the survivors.
- `ImageViewerHost.Dispose()` with live viewers only marks the host; the release is deferred to the last lease.
- A borrowing host never disposes what it does not own, so it keeps serving new viewers while the real owner stays alive.
- `ImageViewerRuntimeServices` releases only the render service it created (`ownsRenderService`); a container-provided render service stays container-owned.
- DI lifetimes mirror those roles: application-lifetime singletons for stateless shared services, scoped for host/runtime/render/viewer inside a window scope, and no transient registrations for disposable resources. Within one scope every render-service interface resolves to the same instance, so a scope owns exactly one tile cache.

## Control Theme Ownership

The control's colors live in `Themes/ViewerTheme.{Dark,Light,HighContrast}.xaml` — never inline in a control's XAML. Every color reference inside the controls is a `DynamicResource` on a `Viewer*Brush` key, so replacing the dictionary re-skins a live control without reloading it.

The precedence trap this design works around: `FrameworkElement.Resources` is searched **before** `Application.Resources`, so a theme dictionary merged into a control's own `Resources.MergedDictionaries` **shadows** any same-key resource the host defines at application or window scope. Consequences:

- Each control (`.xaml`) merges `ViewerTheme.Dark.xaml` into its **`UserControl.Resources`** so it renders standalone — the unit-test harness has no `Application`, and a missing dictionary would resolve brushes to `null`. The dictionary must **not** go on a child element's `Resources` (e.g. the root `Grid`): a child's resources are searched first, so the control-level swap would be shadowed and the theme would appear not to change.
- Hosts override through the control, not around it: `ImageViewer`/`AdaptiveImageViewer`/`Volume3DViewer` expose `Theme` (a `ViewerThemes.Theme`) and `ThemeDictionary`. Setting either swaps the control-local dictionary in place via `ViewerThemeSwitcher.Apply`.
- `ViewerThemeSwitcher` tracks the dictionary it last installed per element (weak table). `Source` alone cannot identify a host dictionary, so **every** replacement goes through the tracked slot: the previous custom dictionary is removed before the new one is inserted. Without that, a second `ThemeDictionary` assignment would be inserted at index 0 while the first custom dictionary — still at a lower index — kept shadowing it, and `ThemeDictionary = null` would not restore the built-in look.
- `ViewerThemes.Apply(Application.Current.Resources, …)` mounts a dictionary at application scope for consumers that resolve brushes themselves; it does not reach into a control's own resources.
- `AdaptiveImageViewer` also propagates its theme to the nested `ImageViewer`/`Volume3DViewer` instances it creates, so one property switch re-skins the whole stack.
- `ViewerThemeKeys` exposes `ComponentResourceKey`s for hosts that prefer per-key override over a whole dictionary.

`ViewerThemeTests` guards the resolution of every theme brush without an `Application`, that switching a built-in theme changes resolved brush colors, that repeated switches replace (never accumulate) the dictionary, that a host-supplied dictionary takes over completely, that a **second** host dictionary still wins, that clearing it restores the built-in default, and that `AdaptiveImageViewer`/`Volume3DViewer` actually re-resolve their own brushes on a theme switch.

## Auto-Save Recovery Across Restarts

An unsaved document is written to `autosave-<DocumentId>.ivsession`. `DocumentId` is generated per process, so a restart cannot find the previous run's file by name alone — `recovery-index.json` (see `ImageViewerRecoveryIndex`) records every auto-save file that has been written on this machine, and recovery accepts an on-disk candidate only when the index vouches for it **and** the snapshot is not owned by a live session:

| Candidate source | Accepted? | Why |
| --- | --- | --- |
| This window's own file name (`autosave-<myDocumentId>`) | yes | Live document in the current process. |
| Indexed path that still exists on disk **and** whose owner's heartbeat is stale (or absent) | yes | The previous run's unsaved document — this is what makes recovery survive a crash. |
| Indexed path still held by a live session (`LastHeartbeatUtc` fresh and `OwnerInstanceId` ≠ mine) | no | Another window has that document open right now; offering it would restore a document that is not orphaned. |
| `autosave.ivsession` (legacy shared name) | only if neither of the above matched | Upgrade fallback for builds that wrote every unsaved document to one shared file. |
| Un-indexed, non-legacy `*.ivsession` | no | Belongs to another window/process; adopting it would restore the wrong document. |

**Ownership / heartbeat.** Every entry carries `OwnerInstanceId` (a per-window identity, distinct from `DocumentId` which changes meaning once a project path exists) and `LastHeartbeatUtc`, refreshed on every successful auto-save. A snapshot is recoverable when it is not owned by this instance *and* its last heartbeat is older than `3 × AutoSaveInterval` (floor 30 s). A window that exits **cleanly** calls `ReleaseRecoveryOwnership()` (from `OnUnloaded` and from the lifetime disposal path), so a document the user deliberately closed is not offered at the next start; a window that **crashes** never reaches that call and its stale heartbeat makes the snapshot recoverable again.

**Index concurrency.** The index is one file shared by every window/process on the machine, so all of `Register`/`Unregister`/`Prune`/`Write` run their whole read-modify-write inside a machine-wide named `Mutex` (`Global\ImageViewerRecoveryIndex-<sha256(directory)[..16]>`), and every write is atomic (temp file + `File.Move(overwrite: true)`). Without the lock, 16 concurrent registrations collapse to a single surviving entry; without the atomic replace, a concurrent reader can observe a half-written JSON and degrade the whole index to empty.

**Cleanup scope.** `GetRecoveryCleanupPaths` cleans only the files this document produced: the current auto-save name, the name recorded in `ImageViewerAutoSaveController.LastWrittenAutoSavePath` (the pre-save name, which changes from `autosave-<DocumentId>` to `autosave-<name>-<hash>` once a project path exists), the legacy name, the shared `autosave.ivsession`, and the adopted `_recoveryFilePath`. It must **not** enumerate `autosave-*.ivsession` — that directory is shared with other windows, so a sweep makes saving one document delete another's recovery file.


## Undo/Redo Failure Semantics

`UndoRedoManager` records a command **only after it succeeds**. The stacks therefore always describe edits that actually happened:

| Operation | Success | Command throws |
| --- | --- | --- |
| `Execute` | command pushed to undo stack, redo stack cleared | nothing recorded — undo stack unchanged, redo stack **not** cleared, exception propagates |
| `Undo` | command moved undo → redo | command stays on the **undo** stack (`CanUndo` remains true, `CanRedo` stays false) |
| `Redo` | command moved redo → undo | command stays on the **redo** stack (`CanRedo` remains true, `CanUndo` stays false) |

The earlier design moved the command across stacks *before* invoking it; a throwing `Undo` then left the command sitting on the redo stack, so `CanRedo` claimed an edit that was never reverted. The rule now is: **a failed operation leaves its stack entry where it was, so the failing action stays retryable and no false "already done" state is exposed.**

Because the stacks stay consistent, the callers do not need to repair state — they only need to not crash. Both entry points (`RoiEditController.Undo/Redo`, which the Ctrl+Z/Ctrl+Y handler in `EditInteractionFlow` delegates to through `IImageViewerEditInteractionHost`) wrap the call in `TryRunHistoryOperation`: on failure they log via `LogNonCriticalError`, show `StatusUndoRedoFailed` with `StatusHintKind.Error`, and skip the refresh plus the "已撤销/已重做" hint. The keyboard path no longer calls the manager directly, so a throwing command cannot escape into the key handler.

Guards: `UndoRedoManagerTests` (14 direct tests, including all three throwing paths, the retry path, depth eviction and change notification), `RoiEditControllerTests` (failure logs and does not claim success; success still refreshes and hints), and the two `UndoRedoManager_When…Throws_…` tests in `ImageViewerMemoryLeakTests`. Reverting to the old "move-then-invoke" ordering makes three of them fail.

## Migration Order

1. Define a framework-neutral contract for each new capability.
2. Add the implementation and deterministic tests in the core project.
3. Add a WPF adapter and preserve the public WPF API.
4. Move an existing capability only after its WPF dependency has been isolated behind that adapter.

The ROI domain base types now live in `ImageViewer.Core` while keeping their original `ImageViewer.Models` namespace: `RoiBase`, `RoiColor`, `RoiColors`, and `BaseViewModel` (`ImageViewer.Common`). `ImageViewerControl` keeps `[TypeForwardedTo]` entries for all of them plus the new `RoiDisplayNameResolver`, so already-compiled third-party plugin assemblies keep resolving the old assembly-qualified names. The earlier justification for leaving ROI types in the WPF assembly ("ROI classes use WPF coordinate and color types") no longer held: `Models/` has 53 files and only two of them touch WPF at all (`VolumeData`, `VolumeIntelligenceModels`, `BitmapSource` only), while ROI geometry uses `PointD` and color uses the model-owned `RoiColor` struct.

`RoiBase.DisplayTypeName` no longer references the localization resources directly. Core exposes `RoiDisplayNameResolver`, and the control assembly installs its `RoiDisplayNameLocalizer` through a module initializer, so "loaded assembly implies localized display names" still holds without Core depending on UI. Without an installed resolver (headless Core usage) the name falls back to the CLR type name.

The remaining `ImageViewer.Models` types (ROI subclasses, volume models) still live in `ImageViewerControl`; moving them is the next step, not a prerequisite. Four executable guards keep these boundaries honest: `CoreArchitectureBoundaryTests` (Core references no WPF/rendering assembly and no `using System.Windows`), `ModelsNamespaceBoundaryTests` (per-type scan of both assemblies, with a self-check so it cannot pass vacuously), `RoiDisplayNameLocalizationTests` (the localization wiring cannot silently degrade to type names), and `RoiDomainModelTests` (ROI domain types are subclassed, cloned and asserted in a WPF-free `net8.0`/`net10.0` test project).
